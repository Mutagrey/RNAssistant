# UI RNAssistant: прототип и порядок переноса

Статус: **внутренние экраны ещё переносятся**, 2026-10-19. Визуальный эталон —
прототип после коммита `403b375d`. Владелец документа — presentation-слой `web`; предметные
контракты остаются у документов, перечисленных в [карте документации](README.md).

Документ действует до завершения переноса согласованного дизайна. При внедрении
каждого сценария актуализировать его раздел; после переноса оставить здесь только
действующие правила UI, удалить временный прототип и ссылки на него.

## Открыть и проверить предложение

[Открыть прототип](../prototypes/ui/index.html) обычным браузером. Нужны соседние
CSS/JS-файлы и локальные зависимости из `web/`; сборка, npm, внешняя сеть, модель и Office не требуются. Альтернативно из корня:

```sh
python3 prototypes/serve_ui.py
```

Демо: `http://127.0.0.1:8897/`; текущий рабочий UI без Office bridge:
`http://127.0.0.1:8897/web/`. Для сравнения с заполненными экранами:
`http://127.0.0.1:8897/product-preview.html`. Кнопка «Сравнить рядом» открывает
демо и рабочий UI в двух панелях; «Запустить пример чата» отправляет пример через
рабочий обработчик. Страница загружает тот же
`web/index.html`, JS и CSS через `/preview/web/` и подключает отдельный mock bridge
до штатной инициализации. Сценарии «Заполнено», «Пусто», «Ошибка чтения» хранят
данные только в памяти вкладки. Демо и mock bridge берут тексты чата, навыка,
VBA, отчёта и исходных файлов из одного preview-only `prototypes/ui/fixtures.js`.
Начальный чат содержит typed итог запуска с `Reason=model_done`, Markdown-таблицу и карточку материала;
его карточка открывает отчёт через штатное чтение точной версии. Отправка текста
в mock показывает этап, поток ответа и итог через рабочие обработчики чата;
ответ помечен как смоделированный. Каталог даёт Markdown, HTML, JSON, PDF,
изображение, коллекцию и текст для проверки рабочих просмотров. Mock отвечает по
действующему bridge-контракту;
действия вне смоделированного набора завершаются явной ошибкой. Сейчас можно
просматривать чаты и отправлять текстовый пример без модели, открывать
материалы, Библиотеку, VBA и проект. Preview подключает пример Data Templates
через browser adapter: редактирование шаблона и словаря, обработка в Worker
и просмотр результата проходят штатными обработчиками. Проектные чаты и цикл
публикации плагина смоделированы в памяти и явно помечены; модель,
Office-действия и native-проверка публикации здесь не запускаются. Data Templates
остаётся изолированным iframe, но общая оболочка показывает дерево и компоновку
проекта по образцу демо.
Оба адреса раздаются одним сервером без кэша, поэтому вкладки можно сравнивать
после обновления страницы. У рабочего UI вне Office нет WebView bridge: его пустые
и недоступные состояния честные, а нативные действия здесь не выполняются.
Сервер нужен только для просмотра, не является частью архитектуры продукта. Демоданные живут в памяти вкладки; перед перезагрузкой
с несохранёнными черновиками браузер запрашивает подтверждение. Ширины панелей
сохраняются отдельно в localStorage прототипа.

Верхняя полоса относится к обсуждению дизайна, а не к будущему продукту:

- **Интерфейс:** основные сценарии на демонстрационных данных.
- **Карта экранов:** Сгруппированные экраны и подэкраны, «сейчас → предлагается»,
  объяснение изменения и переход к соответствующему представлению.
- **Компоненты:** используемые на этих же экранах элементы и правила композиции.
- **Внедрение:** владельцы, заменяемые пути и минимальные проверки.
- Переключатели темы, ширины и демонстрационного состояния позволяют проверить
  обычный, пустой, ошибочный, выполняющийся и неподтверждённый сценарии.

Инвентаризация находится в `prototypes/ui/screen-map.js`: текущий экран, новое
место, маршрут, существующий DOM-id/feature owner и причина переноса. Основание —
`web/index.html`, тематические `app-*.js` и shared Data Templates UI. Это карта
представлений, не каталог новых runtime-возможностей.

Просмотрщики JSON, текста/Markdown, изображений, PDF и задач взяты из `web/`,
редакторы используют штатный CodeMirror, навигация демо и продукта — общий
`web/js/app-navigation-tree.js` с единым ARIA tree. Вкладки редакторов и их
полоса — `web/js/app-editor-tabs.js`, меню действий «⋯» —
`web/js/app-action-menu.js`; оба используют `web/css/app-product-components.css`.
Иконки задаёт `web/js/app-icons.js`: статическая разметка использует `data-rna-icon`,
динамическая — `RNAssistantIcons.render` через дерево или `P.icon`. Плагин с
`icon.svg` передаёт в rail только проверенные SVG-пути; их рисует тот же реестр.
Библиотека использует общий `app-library-groups.js`: тип → группа по namespace
и семейству (`excel.*`, `common.resources_*`, `common.plan_*`), при этом ID
инструментов и навыков не меняются. Общие кнопки,
наведение, вкладки, таблицы и строки дерева оформлены в
`web/css/app-product-components.css`. «Все материалы» остаётся отдельной кнопкой
вне ARIA tree, но использует общие отступы, подсветку и переходы навигации;
при открытом каталоге строка дерева не выделяется. Кнопка свёртывания панели
совмещена с заголовком центральной области при любом размере окна.
В «Материалах» вкладка «Детали» остаётся рядом с «Просмотром»: в ней доступны
метаданные, точный JSON и история версий.
На экране создания плагина форма выровнена слева. Сверху показаны его иконка и
название, которое обновляется при вводе. В заголовке все виды иконок имеют размер
32×32 внутри кнопки 44×44; в боковой панели — 20×20. Нажатие на иконку раскрывает редактор:
базовые значки, каталог сохранённых SVG, удаление пользовательских записей,
описание и кнопку немедленного рисования через модель. Этот же редактор открывается
действием «Редактировать» в меню значка существующего плагина и сохраняет его
название/иконку на панели. Общий выбор «Цвет иконки» доступен в создании и
редактировании: по умолчанию нейтральный цвет текущей темы, исходная палитра SVG
с несколькими цветами/градиентами либо свой однотонный цвет через color picker.
Переключение режима сохраняет исходный рисунок без повторной генерации. Папка исходников стоит
ниже задачи без отдельной декоративной иконки. На широком экране переключатель
дерева здесь скрыт, так как у формы нет дерева; в компактном режиме общий
переключатель остаётся у края. У значков полосы разделов одна всплывающая
подсказка справа; меню плагина предлагает убрать его с панели, а меню `+` —
восстановить скрытые плагины или создать новый. Нажатие самого `+` открывает форму.
Подписи меню обычной насыщенности; ширина короткой подсказки следует за текстом,
а меню с длинным названием растёт до 420 px и затем переносит текст без обрезания.
Действие удаления в меню плагина отделено от названия тонким разделителем и
использует шрифт общей оболочки.
Office, workspace и чат разработки плагина используют общий рендерер сообщений,
Markdown, пустое состояние и стили composer; workspace-specific transport и
доступные действия остаются у соответствующих владельцев. Сообщения всех трёх
экранов имеют один `ChatMessageViewDto`; workspace-проекция раскрывает
принятый v8 ответ без передачи его protocol body в браузер. Tool activity
проходит через тот же безопасный browser-view projector, что и Office.
Ранние сообщения проекта и плагина подгружаются по тем же индексам и размеру
страницы, что у Office; новые snapshots того же экрана сохраняют уже загруженную
раннюю часть выбранной сессии.
Живой ответ модели и сверка keyed DOM-узлов ленты используют общие функции Office;
при поступлении новых сообщений, смене попытки и подгрузке истории сохраняются
неизменённые узлы, раскрытие деталей, фокус и позиция чтения.
Неудачный workspace-запуск без принятого ответа оставляет диагностическое сообщение;
ошибка и неподтверждённый результат остаются видны в старой ленте после нового запуска.
Все три экрана
переносят одну физическую ленту сообщений и одну форму ввода с теми же
textarea/Send/Stop. Черновик и доступные действия переключаются по owner;
Office сохраняет document queue/attachment actions, проект — загрузку файлов,
плагин — source chat. Fork, edit, delete и копирование сообщений доступны в общем
footer всем трём owner; edit использует одну панель composer и прежний черновик
восстанавливается при отмене. Единый ChatView controller в `app-workspace-chat.js`
владеет mount, общей формой, Enter/Send/Stop и общими workspace
approval/question controls. Он направляет события текущему owner; тематические
модули сохраняют transport и состояние своих чатов. Общие controls имеют
нейтральные ID; временный plugin alias к `projectChat*` удалён.
Кнопки «+», планирования, модели и reasoning теперь также являются одними и теми
же DOM-узлами для всех owner; отдельные workspace-копии удалены. В project
«Файл с компьютера» вызывает workspace upload, в Office — document attachment;
модель workspace берётся из общих настроек через тот же picker.
Разрозненные простые рендереры сообщений и вопросов в
`app-plugins.js`/`app-project-chats.js` удалены.
Office, проект и плагин собирают сохранённые сообщения через один iterator и
одни builders DOM-узлов/footers; live-состояние и transport остаются у owner.
Workspace fork сохраняет точный префикс истории и CAS-вложения. Edit заменяет
выбранное user-сообщение, обрезает последующую историю и запускает новый run с
revision guard; delete сохраняет целостность tool exchange. Прототипные
скриншоты и браузерные проверки не квалифицируют Office/WebView2 на Windows.
Возврат формы Office использует собственную DOM-позицию ChatView и не зависит
от расположения диагностики. Неподтверждённый workspace input хранит один request ID
на точную пару workspace/session в общем владельце черновиков; переход между
проектом и плагином не создаёт новый запрос при повторе того же ввода.
Поздний acknowledgement очищает только соответствующий запрос и версию черновика.
Ответы чтения, выполнения и отмены для одной сессии не заменяют уже показанный
snapshot с большей revision. Ожидание ответа проектного или плагинного чата
привязано к точной workspace/session: после выбора другой беседы её ввод доступен,
а поздний ответ прежней не меняет выбранный чат. Поздний ответ создания чата
обновляет дерево, но не переключает беседу после ручного выбора другой.
Ожидающая отмена блокирует Stop только своей сессии; поздняя ошибка отмены не
появляется в другой беседе.
Удаление выбранного чата или истории выбирает следующий экран по текущему выбору;
поздний ответ удаления не открывает прежний плагин после перехода в другой проект.
Загрузка файла занимает один UI-слот и блокирует отправку только в своей сессии.
В другой беседе текст доступен, но выбор второго файла ждёт завершения загрузки;
готовая ссылка и статус относятся к исходной workspace/session и видны после возврата.
Поздний ответ подключения или создания проекта обновляет дерево, но не меняет
проект/чат после ручного перехода; без перехода новый проект открывается как обычно.
Ответы переименования, удаления чата/истории и подключения меняют в текущем
каталоге только затронутый чат или проект: запоздалый снимок не скрывает созданные
параллельно чаты и не откатывает их названия. Ошибка переименования после перехода
не появляется в новой беседе.
Фоновые чтения каталога после запуска и создания чата сверяют локальную ревизию;
если дерево изменилось во время чтения, запрос повторяется перед применением.
Подключение проекта и создание соседнего чата не блокируют ввод в уже открытой
беседе. Отправка во время ожидания сохраняет её выбор; новый чат остаётся доступен
в дереве. В только что созданном чате ввод доступен до обновления каталога.
После отправки форма предлагает «Скрыть»: операция продолжится и обновит дерево.
Закрытие формы не отменяет ожидающее чтение другого чата.
Общий observer читает точную workspace/session, пока запрос не подтверждён или
snapshot сообщает running. Он начинает наблюдение и при открытии уже работающего
чата, продолжает после ошибки отправки и прекращает его после terminal/waiting
состояния либо смены сессии. Запросы чтения не перекрываются; ответ прежней сессии
после переключения отбрасывается. Наблюдение не запускает и не повторяет выполнение.
Во время запуска в процессе панели тот же bridge `progress` доставляет ограниченный
предпросмотр модели проекту и плагину через общий ChatView owner. Каждое событие
проверяется по workspace/session/run и монотонному номеру предпросмотра; опрос
остаётся для reconnect и восполнения пропущенного события. При смене ChatView owner
скрытый observer останавливается; скрытие правого предпросмотра не меняет owner
и не останавливает наблюдение за выполняющимся чатом. Запуск в другом
процессе отдаёт текущий предпросмотр через ограниченное чтение IPC при опросе состояния;
сохранённые сообщения и статус читаются из event stream. Промежуточные токены не
становятся историей чата. Если владелец run недоступен, снимок явно сбрасывает
старый предпросмотр, хотя состояние журнала до восстановления ещё может быть running.
Иконка плагина открывает его исходный проект: слева остаётся дерево проектов и
чатов, общий ChatView занимает центр, а существующий iframe — правую поверхность.
Кнопка правой панели остаётся справа в заголовке центрального чата на широком
экране. При узком наложении та же кнопка появляется в шапке предпросмотра,
иначе её перекрыла бы панель. Сворачивание сохраняет iframe и черновик.
Плагин и HTML-проект используют общую двухуровневую шапку правого просмотра:
верхняя строка выбирает «Предпросмотр», «Контекст», «Возможности агента» или
«Ход работы»; строка ниже называет ресурс и содержит только действия над ним.
Версии и редкие операции плагина находятся в одном меню «Версии»; проверенное
изменение или выбранная старая версия показывают отдельную строку с точным
«Применить» или «Восстановить». Отдельной стрелки закрытия внутри просмотра нет.
Каждый сохраняет свой существующий iframe и
проверки владельца. Обновление HTML пересобирает текущий снимок через прежний
renderer, отзывает выбор Inspector и открытые data leases. Маршрут HTML рядом
с центральным Office-чатом теперь работает для текущего HTML workspace:
«Открыть справа» в «Материалах» или карточка текущей версии в чате переносит
тот же iframe и контролы, а возврат в «Материалы» отдаёт их редактору. Скрытие
сохраняет живой кадр и черновик; смена чата/revision отзывает прежнюю привязку.
Правая диагностика и браузер показываются по очереди. Ширина браузера по
умолчанию 42% доступной области, перетаскивание сохраняет долю, расширение
даёт до 60% при минимуме чата; на тесной ширине работает отдельный правый вид.
История переходов и произвольные ресурсы остаются следующей работой.
Разделитель центрального чата и правого предпросмотра использует общий `.splitter` и
`RNAssistantSplitter` из `app-layout.js`, как дерево и правая панель: одна линия
1 px с прозрачной областью захвата 11 px. В плагине та же физическая линия
проходит через верхнюю полосу проекта; у HTML-браузера поверх неё нет
второй рамки. Перетаскивание остаётся у общего разделителя.
В заголовке центрального чата плагина стоит название выбранной беседы; общая
кнопка `+` и история находятся в дереве проектов. «Применить» видно только при
отличии проверенного пакета от активной версии или при отключённом плагине.
Вложенный заголовок чата не резервирует место под общую кнопку навигации:
его левый отступ остаётся 12 px на всех ширинах.
Оба экрана используют одну workspace-сессию и общий выбор. Черновик текста,
mode и reasoning хранится в общем состоянии чатов по паре workspace/session:
изменения на экране проекта видны при открытии той же беседы в плагине и наоборот.
Фоновое обновление другого экрана не переписывает смонтированный чат. История
исходников доступна во время выполнения; поздний ответ не возвращает выбор
старой сессии.
Подтверждение отправки в workspace и Office очищает только ту версию черновика,
которую отправляли; более поздний ввод сохраняется даже при том же тексте.
Office-черновик имеет отдельную identity по chat ID, его новые вложения остаются
после позднего подтверждения. Текст и настройки workspace-черновика, Office-текст
и ID подготовленных вложений сохраняются в защищённом CurrentUser-DPAPI файле
по точной сессии. После пересоздания WebView runtime проверяет staged-вложения;
недоступное вложение явно отмечается, его содержимое не подменяется. ID
неподтверждённой отправки также восстанавливается для безопасного повтора.
Содержимое черновика не записывается в localStorage или историю чата.
Окно ввода чата сохраняет прежнюю высоту в две строки с ростом до шести;
длинная переписка не сжимает его панель кнопок. Индикатор контекста скрыт, пока
не известны входные токены и ёмкость окна, и появляется после получения usage;
меню действий, значки и отступы соответствуют демо. Лента рабочего чата перенесена
на существующие message/activity projections: компактные материалы и таблицы,
отдельные группы соседних действий, раскрытый активный этап и общая история
только после явного финального ответа. Остановка без финала оставляет комментарии
видимыми; предупреждения разделяют группы, исходная ошибка не заменяется успешным
обновлением. Runtime evidence, вопросы и подтверждения сохраняют штатные владельцы.
Раскрытия и фокус переживают обновления; закрытая общая история освобождает DOM,
сохраняя только состояние раскрытий. Проверено адресно в Chromium, включая узкую
ленту и темы; Windows/WebView2 не квалифицированы.
Этапы используют значок, отдельный счётчик и shimmer из демо; активное действие —
вращающийся индикатор. Движение отключается после terminal runtime state,
при reduced motion и в forced colors для текстового эффекта. Источник и подробности
действия раскрываются в компактной карточке. Боковой «Ход работы» показывает шаги
из текущей проекции и открывает журнал точного запуска. Обычный завершённый ответ,
включая приветствие и чтение без изменений, не получает служебную карточку:
`GoalVerification=not_assessed` и счётчики остаются в typed state, завершение ответа
не подтверждает достижение цели. В ленте ошибки и unknown показаны компактной
строкой со значком и ссылкой на подробности, вне свёрнутой истории. Уточнение и
блокировка имеют короткую подпись над текстом без отдельной рамки; единая форма
вопросов не оборачивается дополнительными панелями и не повторяет одинаковый заголовок.
Office, Project и Plugin используют одну форму `app-questions.js`: общий мягкий
фон, тонкая рамка и радиус `--radius-lg` из демо. Одновременно виден один вопрос;
вверху — счётчик `1 / 2` и компактные стрелки назад/вперёд. Варианты — строки
с разделителями, описанием и отдельной отметкой рекомендации. Одиночный выбор
сразу переключает вопрос, последний отправляет весь набор. Для нескольких
вариантов и своего текста служат «Далее»/«Готово». Стрелки сохраняют ответы;
стрелки клавиатуры внутри radio-группы меняют выбор без перелистывания.
«Пропустить» относится к текущему вопросу и переключает дальше; крестик с
подсказкой «Пропустить всё» отправляет явный пропуск всего набора. Свой ответ —
компактное однострочное поле с возможностью увеличить высоту. Цвета, радиусы,
кнопки и значки принадлежат общей системе демо;
рекомендация сама ничего не выбирает. Single/multiple и доступность своего
ответа следуют typed question contract. Поле содержит placeholder «Ответ…» и
доступное имя для screen reader; отдельной подписи и подсказки о переходе нет.
Можно явно пропустить отдельный вопрос или весь набор. Пустой ответ без пропуска
показывает ошибку у формы и открывает вопрос с переводом фокуса. Отправка блокирует
повторный клик и показывает ожидание. Карточка исчезает только после успешного
intake и не открывается повторно от устаревшей pending-проекции; ошибка остаётся
у кнопки. Выбор, текст и текущая страница сохраняются при обновлениях и переходах между
чатами в памяти, с привязкой к exact chat/run/question set. Повтор неизменённого
ответа сохраняет operation/request ID. Новые принятые ответы отображаются
обычным текстом «Вопрос: … / Ответ: …»; пропуск не подменяется выбранным вариантом.
Ctrl/Cmd+Enter выполняет «Далее»/«Готово», обычный Enter в своём ответе переносит строку.
Это применяет документированный паттерн
[Codex App Server: user input](https://learn.chatgpt.com/docs/app-server#toolrequestuserinput)
с отдельным запросом и подтверждением ответа; точный desktop layout не копируется.

В текущем Conversation v8 частичный, неподтверждённый и невыполненный итог
`finish.results` выводится как оценка модели с точными ссылками на результаты;
`GoalVerification` остаётся `not_assessed`. Сохранённый `reflection` показан
как шаг истории без повторного комментария и без превращения в tool result.
Актуальная ошибка/unknown остаётся плашкой у ввода, подтверждение — отдельной
панелью с общей семантической заливкой в обеих темах; успешное копирование
подтверждается коротким toast, ошибка копирования закрывается вручную.
Плашка «Ресурсы» над вводом и её меню удалены: доступ через карточки ленты,
«Материал чата» в меню ввода и раздел «Материалы». Список изменений использует
компактную свёрнутую строку, отступы и цвета демо; пустой список не оставляет зазора.
Предварительные и недоступные сравнения раскрываются сразу, чтобы не скрыть ограничения.
Демо также оставляет предупреждения перед итогом вне свёрнутой истории.
Подпись «Повтор помог» не
выводится по совпадению названий инструментов: текущая проекция не задаёт связи
между отдельными попытками; исходные ошибки остаются доступными.
Набор действий и активное представление задаёт владелец экрана. PDF получает
созданные для демо изображения страниц и текст: это не PDF-декодер в браузере.
Установка пакетов, COM, исполнение инструментов и провайдеры остаются демопримерами. JSON-проверка шаблона проверяет только синтаксис.
Настоящий API-ключ вводить не нужно; значение ключа не сохраняется. Выбор локального
файла читает только его имя. Выгрузки содержат только демонстрационные данные.

## Предлагаемая структура

| Раздел | Содержимое | Основные переходы |
|---|---|---|
| Рабочая область / Документы Office | Дерево документов с чатами внутри | Выбор чата → переписка; документ → новый чат / открыть / удалить историю |
| Рабочая область / Проекты | Подключённые workspaces, непосредственно внутри — чаты; без подпапок | Подключить/создать workspace, выбрать чат, удалить историю |
| Данные и шаблоны | Источники, шаблоны, обработка | Источники → шаблон/соответствия → обработка → результаты |
| Материалы | Каталог, просмотр, код, версии, экспорт | Каталог → материал; обсудить → чат с контекстом |
| Библиотека | Навыки, инструменты, инструкции | Список → редактор → проверка; установка → подтверждение |
| VBA | Живые модули связанного документа | Код → изменения → сохранение; запуск/восстановление → подтверждение |
| Настройки | Подключение, модель, агент, интерфейс, защита, помощь и обслуживание | Ошибка запуска → подробности действия в чате |

Чат принадлежит документу. Рабочая папка и проект выбираются независимо: открытие
проекта не переключает документ и не включает файлы в контекст модели. Live VBA
не переносится в каталог материалов. Создание UserForm исключено из предлагаемого
интерфейса: удалены кнопка, экран и обработчик прототипа; это не изменение runtime. Самостоятельный Data Templates использует
те же экраны без оболочки ассистента.

Слева — узкая полоса **52 px** только с иконками разделов, подсказками и
доступными названиями; настройки закреплены снизу. Рядом одна общая панель дерева,
содержимое которой зависит от раздела:

- Рабочая область (иконка дома): меню «Документы Office / Проекты» вместо заголовка,
  затем дерево. Выбранный раздел виден в кнопке меню; отдельных строк переключения нет.
  Документ имеет иконку приложения Office; проект — папки. У чатов иконок нет.
  Вложенных проектов/подпапок и направляющих линий нет.
- Материалы: группы по принадлежности → HTML-проекты и остальные материалы с иконкой формата.
- Библиотека: навыки / инструменты / инструкции → определения.
- VBA: модули / объекты → код. Связанный документ указан в шапке, без лишнего уровня дерева.
- Данные и шаблоны: источники, шаблоны, словарь, обработка и результаты.
- Настройки: подключение, модель, контекст и вложения, агент, интерфейс, защита, помощь и обслуживание.

Версия приложения стоит серой строкой после разделителя внизу меню, открывающегося
при наведении на значок настроек в левой панели.

Переключение раздела возвращает его последний экран; поиск и свёрнутые группы
запоминаются отдельно. Ширина дерева общая для разделов и синхронизируется между
вкладками этого origin через storage event; ограничения узкого окна не меняют предпочтение. Второго списка в редакторе нет.
Новый чат и новая ветка появляются первыми внутри своего документа/проекта;
выбранная строка остаётся видимой после перестройки дерева.
Логотипа/подписи RNAssistant над деревом нет. Поиск и «+» стоят справа в заголовке;
поиск рабочих чатов и проектов, Библиотеки, VBA, материалов и настроек использует один
обработчик: поле раскрывается справа от кнопки и сворачивается при потере фокуса.
Непустой фильтр сохраняется: кнопка выделена, подсказка содержит запрос. Повторное
открытие позволяет изменить фильтр; Escape или повторное нажатие очищает его.
У материалов одно поле поиска для дерева и каталога и одно меню добавления: в
каталоге оно стоит в заголовке, при просмотре материала — в дереве.
Создание документа Office находится
над деревом, меню содержит иконки Excel, Word, PowerPoint и Outlook.
Путь/подробности показываются в подсказке. Действия строк появляются при наведении
или клавиатурном фокусе; на сенсорном устройстве остаются видимыми. Технические
размеры JSONL/CAS показываются только на значке предупреждения хранилища, а
выбранная строка не меняет заливку при наведении. Документы
сохраняют действия нового чата, открытия/активации и удаления истории; чаты —
переименования и удаления. Выполняющийся чат нельзя удалить. Удаление истории
не означает удаление файла или папки.

Круговой индикатор в строке чата означает выполнение. Точка нового ответа
появляется при завершении в фоне и снимается при открытии чата. Ожидание
подтверждения показано отдельно. При production-переносе эти состояния брать из
существующих projections, не выводить успех из самого завершения запроса.

Кнопка без подписи справа в заголовке открывает/закрывает боковую панель и
восстанавливает последнее её представление. Она не ограничена экраном контекста.
`RNAssistantPanelToggle` из `app-panel-toggle.js` владеет общей кнопкой панелей:
иконкой, подсказкой, `aria-expanded`/`aria-controls` и обработкой нажатия.
Её используют навигация, инспектор чата и правый предпросмотр плагина, включая демо.
Видимость и сохранение состояния остаются у владельцев раскладки; отдельного
переключателя `</>` с checkbox и стилями плагина нет.
Разделы правой панели выбираются меню её заголовка; отдельного меню этих разделов
в заголовке чата нет. Оно использует тот же `panelMenu`, что и «Документы Office»:
иконка, подпись, стрелка, отступы, hover/focus и выбранный пункт общие.

### Диагностика в существующей правой панели — 2026-10-23

Owner — application/chat UI, `app-chat-inspector.js`. По уточнению пользователя
и фотографиям рабочего интерфейса основой остаётся эта панель и её четыре пункта:
**Контекст / Возможности агента / Использование контекста / Ход работы**.
Отдельная оболочка и второе дерево шагов отклонены; экспериментальный макет удалён.
[Исходный UI/UX-план](proposals/RNAssistant_Diagnostics_UIUX_Plan.md) сохранён как
предложение; он не отменяет это решение и действующие runtime-контракты.

- Меню получает одну иконку из статической разметки; JS меняет только иконку
  выбранного раздела в заголовке. Повторный render не добавляет SVG.
- **Использование контекста:** сверху последний вход по API и доступное окно,
  ниже компактная полоса долей и раскрываемые группы: диалог/текущий запрос,
  инструкции, инструменты/навыки, ресурсы, формат/прочее. Группа показывает
  оценку токенов и долю, внутри — исходные разделы и ограниченные previews.
  Источник состава — существующий `inspectPromptContext(includeRaw=false)`:
  это **оценка следующего запроса**, включая черновик, а не измеренное разложение
  последнего API usage. Доли считаются от суммы известных включённых частей;
  резервы и исключённые источники показаны отдельно. Неизвестный размер не
  становится нулём, body delivery из размера не выводится. Переключение чата,
  вида или закрытие панели отменяет pending request и отбрасывает поздний ответ.
  Кнопка фактического запроса открывает существующий Model Context Inspector.
- **Возможности агента:** состав остаётся у `getAgentArsenal`; навыки — компактные
  раскрываемые строки, инструменты — группы существующей классификации Библиотеки.
  Описание занимает одну строку до раскрытия; полное описание, public ID и
  confirmation видны в деталях. Historical/pending/restriction не скрываются.
  Эти группы не дублируются в верхнем меню панели.
- **Ход работы:** сохраняются нумерованные шаги runtime. Разные StepId не
  склеиваются, даже если сообщение одинаковое или отсутствует. Раскрытие шага
  показывает каждый вызов, его собственный статус и результат; переход в журнал
  использует точные chat/run/step/call IDs. После terminal-состояния запуска
  оставшиеся running/waiting одинаково показаны как отменённые в шаге и внутри
  действия; неизвестный эффект остаётся предупреждением, сохранённые статусы
  не переписываются. Переход к запросу/ответу фильтрует
  существующий список сохранённых запросов по точным RunId + StepId. Если запрос
  не найден на странице, это сказано явно и доступно «Ранее»; чужой последний
  запрос не подставляется. Длинный итог запуска раскрывается отдельно.

Из ленты Office-, проектного или плагинного чата значок «Открыть шаг» у действия выбирает точные RunId +
StepId, раскрывает и выделяет шаг в этой же панели. Переходы используют общий
значок часов из пункта «Ход работы», уменьшенный для ленты до 13 px. Значки
действий также остаются 13 px; кнопка перехода выровнена по первой строке текста и не увеличивает
высоту компактной строки. Значок у итогового ответа
или группы сообщений открывает запуск: отсутствующий StepId не заменяется
последним шагом. Выбранный запуск закреплён при новых сообщениях; кнопка
«К последнему запуску» возвращает текущую проекцию. Используется загруженная
часть истории, без второго store: если нужного шага нет, показано явное сообщение
и переход в журнал с исходными IDs. Закрытие/Esc возвращает фокус на исходную
кнопку; переключение чата сбрасывает выбор, устаревшая кнопка его не переносит.
Один DOM инспектора перемещается вместе с общим ChatView. В проекте доступны
«Контекст», «Возможности агента», «Использование контекста» и «Ход работы»; в плагине к ним добавляется «Предпросмотр». Переключение
не пересоздаёт iframe и не меняет черновик. Компактные строки шагов и раскрытия
используют тот же renderer, отдельный список действий плагина удалён. На узком
экране инспектор открывается поверх чата с кнопкой возврата.

Owner: Web chat Inspector presentation. Источник workspace-представления —
существующий snapshot выбранной сессии через `RNAssistantWorkspaceChat`, без
второго store. Контекст показывает папку и документ запуска из этого snapshot;
история фильтруется по RunId. Переход закрепляет owner + workspaceId + sessionId,
а при смене поверхности кнопки ленты получают новый owner даже для той же сессии.
Старые ссылки и результаты Office не подставляются в workspace-чат. Если шаг
workspace не загружен, панель предлагает загрузить предыдущие сообщения.

Office, project и plugin используют общий renderer карточки запуска для сохранённых
действий, итогового ответа и текущего вывода. В workspace просмотр результата
читает свою сессию по точным workspaceId, sessionId, RunId и ToolCallId;
переход на другую поверхность не переносит поздний ответ в новый чат.

Возможности workspace берутся из `contextReceipt.Arsenal` выбранной сессии:
тот же компактный список навыков и группы инструментов, краткое описание до
раскрытия, полное описание и причина недоступности внутри, признак подтверждения
у инструмента. Это состав подготовленного запроса. Чужой текущему запуску RunId
помечается как предыдущий запуск; отсутствие снимка не превращается в нулевые
счётчики. До первого подготовленного запроса явно показано отсутствие состава.
Каталог `Available` не выдаётся за подключённые навыки; доступность повторно
проверяет runtime перед выполнением. Office-запросы для workspace не вызываются.

**Запрос / ответ модели** доступен из шага workspace, а из нижней части
«Хода работы» можно открыть запросы выбранного запуска. Используется тот же
просмотрщик и сохранённые `llm.request` / `llm.response` события с полными CAS-телами.
Typed queries `getModelContext` / `getModelContextPayload` передают точные
workspaceId + chatId; ответ подтверждает оба значения, а leases закреплены за
`model-context:<workspaceId>`. Чужая или отсутствующая привязка отклоняется.
Диагностическое чтение не запускает модель, не переключает Office-документ и
доступно при недоступной исходной папке подключённого проекта. Смена беседы,
проекта или владельца закрывает просмотр, отменяет загрузку и освобождает lease;
поздний ответ не переносится в новую беседу. Изменение размера сохраняет тело и
раскрытия, возврат восстанавливает фокус на кнопке шага.
Workspace использует только сохранённые запросы; «Следующий запрос» скрыт.
Пустой журнал явно отмечен, последний Office-запрос не подставляется.
**Использование контекста workspace** читает typed `contextUsage` из snapshot
выбранной сессии: последний принятый ответ, его вход/выход/общий расход по API.
У параллельных вызовов счётчики принадлежат одному ответу; отсутствие usage в новом
ответе не подменяется прежними числами. Размер окна берётся только из того же
RunId; расход предыдущего запуска явно отмечен. Полоса показывает занятую и
свободную доли окна, а не вымышленное разложение токенов по источникам.
Отдельно показаны оценка подготовленного контекста из сохранённого receipt,
сведения об исключениях/сжатии и переход к запросам соответствующего шага.
Оценка следующего запроса workspace и точные доли по источникам ещё недоступны.

**История и диагностика workspace** открывает существующий журнал в настройках
с точными owner + workspaceId + sessionId + run/step/call. «Показать весь чат»
снимает фильтр запуска, сохраняя исходную сессию. Raw-события, lazy payload и ZIP
экспорт используют тот же event/CAS path и подтверждают workspace + chat в ответе.
Чужие и запоздалые результаты отклоняются; leases закрываются с исходным owner.
Office-only журнал VBA недоступен в workspace. Отдельного хранилища и второго
просмотрщика нет; Windows/WebView2 delivery остаётся открытой проверкой.

**Чтение запроса и ответа** занимает эту же правую панель. Размеры «В панели»,
«Шире» и «Весь экран» меняют раскладку одного смонтированного просмотра:
выбранный запрос, раскрытия, загруженные тела и прокрутка сохраняются, повторного
чтения payload при изменении размера нет. Широкая панель меняется разделителем,
включая клавиатуру. В полноэкранном режиме фон недоступен для ввода, Tab остаётся
в просмотре; Esc сначала возвращает прежний размер, затем — исходную панель и
фокус на кнопку шага. Смена чата или владельца закрывает просмотр и отменяет reads.

Экран использует общие цвета, размеры элементов, иконки, вкладки и document
viewers. На виду — источник, выбор запроса и вкладки «Сообщения / Ресурсы /
Ответ / JSON»; историю и поиск по короткой ссылке раскрывают отдельно.
В проекте и плагине отсутствует неактивный выбор источника: селектор сохранённого
запроса, обновление и скачивание занимают одну строку. При возврате в Office
выбор источника восстанавливается; в предварительном контексте селектор
сохранённого запроса скрыт. Сообщения показывают исходный номер, понятную роль и
короткий preview в компактных строках с разделителями. При наличии согласованной
оценки состава они сгруппированы по разделам; «Порядок отправки» возвращает исходную
последовательность. Раскрытый текст отмечен спокойным цветовым акцентом.
«Свернуть» закрывает сообщения и разделы одним действием.
Сначала раскрывается содержимое; receipt, операция, поля protocol и исходный JSON
собраны в «Данные сообщения». Базовая оценка токенов видна у каждого сообщения;
без сохранённой оценки показываются только символы JSON. Точный размер JSON
остаётся в данных сообщения;
отсутствующие сведения о полноте источников не превращаются в «полностью».
Текст сохранённого ответа виден сразу на вкладке «Ответ». Для v8, включая строгую
обёртку `response`, отдельно читаются `message`, действие и сохранённые
`reason`/`decision`; результаты `results` помечены как оценка модели.
Пустой `message` раскрывает пояснение действия; это сообщение модели, а не
доказательство выполнения инструментов. Исходные тела остаются
доступны целиком. Размер строки в полном экране ограничен
для чтения. Стрелки переключают вкладки; недоступные вкладки ответа/ресурсов
отключены для ещё не отправленного предварительного контекста.

Сохранённые источники сообщения вынесены из технических полей в раскрытие
«Источники и полнота» перед его содержимым. Строки используют общий компонент
демо; наблюдение ресурса показывает отдельно включение тела в сообщение,
запрошенное/наблюдаемое покрытие и полноту фрагмента, представления и источника.
Границы покрытия подписаны без пересчёта сохранённых start/end; точные значения,
сведения провайдера и идентификаторы доступны в «Сведениях о чтении».
Вложения раскрывают размер, MIME, страницы, причину и отдельный отпечаток.
Открытие связанного ресурса и возврат сохраняют раскрытия того же запроса.

«Сохранённые пропуски» стоят отдельно от включённого состава и объединяют исключённые сообщения
и части вложений. Счётчик относится к записям, а не предполагаемому количеству
пропущенных страниц/ресурсов. Список строится при раскрытии, по 50 записей;
локальный оригинал читается только по отдельному действию. Неточные/отсутствующие
сведения не дополняются по длине текста: несколько записей с одним MessageIndex
не дают выбрать одну из них как источник сообщения. Пропуски в metadata не означают
отсутствие пропусков при сборке запроса. Это отображение имеющейся трассы;
полнота атрибуции преобразованных сообщений и точные доли токенов остаются открытыми.

**Оценка состава сохранённого запроса.** Новые request-события сохраняют базовую
оценку каждого окончательного сообщения и обвязки формата. Сразу видны полоса долей,
общая оценка и разделы с количеством сообщений, токенами и процентом:
инструкции/каталог, история сообщений, вызовы/результаты, ссылки/состояние ресурсов,
контекст ресурсов, сообщения с вложениями, формат ответа и нераспределённое.
Ссылки и уведомления выделены по typed compiler kind, без поиска маркеров в тексте;
в ранее сохранённой общей группе ресурсов детализация не выдумывается.
Сегмент полосы раскрывает соответствующий раздел. Внутри история раскрывается
по сообщениям прямо до текста, источников и точного JSON. Переключатель
«По разделам / Порядок отправки» сохраняет раскрытые сообщения и источники;
в последовательном режиме строки сводки переходят к исходному сообщению.
Списки создаются при раскрытии по 50 строк, без повторного чтения payload.
Раскрытия и загруженные страницы сохраняются при возврате между вкладками.

Это базовая оценка без калибровки, а не расход API или точная цена тела ресурса.
Сообщения учитываются целиком: инструкции и каталог не разделяются по текстовым
эвристикам, текст с вложениями остаётся одной группой, нераспределённые сообщения
сохраняют свой объём. Исключённые вложения не создают долю. Старые запросы без
сводки показывают отсутствие оценки; несогласованные суммы, повторяющиеся/пропущенные
индексы и неизвестный формат не превращаются в диаграмму. Preview следующего
запроса остаётся отдельным представлением. Точная атрибуция навыков, инструментов,
частей смешанных сообщений и перенос этой сводки в верхний счётчик ещё открыты.

Запоздавшая загрузка относится к конкретному выбранному запросу и представлению:
она не заменяет открытую вкладку и не выводит старую ошибку после переключения.
При выборе другого запроса прежнее тело сразу убирается; ошибка загрузки не
оставляет его под новым номером. Обновление сохраняет возможность раскрыть
ещё не открытые данные сообщения и переиспользует уже прочитанное неизменяемое
тело. Загрузка, отсутствие данных и ошибка показаны отдельными состояниями;
экспорт недоступен во время выбора запроса либо при отсутствии сведений о
сохранённом теле. В узкой панели размер JSON доступен в данных сообщения;
в широкой — также в строке рядом с ролью. Возврат с вкладки ответа или JSON
сохраняет раскрытые входные сообщения и прокрутку того же запроса, включая
загруженные страницы списка. Новый предварительный снимок начинает своё чтение.
В низком окне история
и поиск прокручиваются отдельно от содержимого. Адаптивное сжатие панели не
перезаписывает выбранную пользователем ширину. Возврат фокуса при закрытии
учитывает новую ширину окна, даже если событие resize ещё не обработано.
Скрытый раздел не пересчитывает ширину инспектора до минимума; раскладка закрытого
HTML-предпросмотра не меняет колонки панели диагностики.

Сохраняются раскрытия и прокрутка по представлению текущего чата. Raw payload,
CAS, lease/download owners, журналы и экспорт не заменяются. Общий dock уже
показывает контекст, возможности, расход и шаги всех трёх типов чата. Полный журнал
доступен по точным переходам; preview следующего workspace-запроса, compaction/diff
и causal graph требуют отдельных ограниченных изменений.
Верхний счётчик контекста пока не показывает состав последнего **фактического**
запроса по всем источникам. Базовая сводка нового сохранённого запроса доступна
в его просмотрщике; её доли не нормализуются до числа токенов провайдера.

**История чата — дерево запусков, 2026-10-25.** Owner — Web trajectory /
run journal. Сверху — итог выбранного запуска и обзор шагов. Иерархия:
«запуск → шаг → действие → исходные события». Принятие, выполнение и результат
одного вызова собраны в одной ветке; короткие названия действий видны в заголовке
шага. Обмен с моделью, попытки и служебные записи находятся в отдельных свёрнутых
ветках с менее заметным оформлением. Ошибки и неподтверждённый эффект выделены и
на закрытых родительских ветках. Успех отдельного инструмента не становится итогом
запуска. Номера шагов обозначают порядок в загруженной выборке.

Группировка использует сохранённые идентификаторы внутри точного запуска;
отсутствующую привязку к шагу можно восстановить только по однозначной связи
вызова/попытки. Непривязанные и конфликтующие события остаются явно отдельными.
Фильтр сохраняет дерево предков; меню позволяет раскрыть шаги, первые 50 проблем
с их предками или свернуть всё. Возврат и обновление сохраняют раскрытия и явные
сворачивания. Сворачивание родителя отменяет загрузку тела и освобождает скрытые
просмотрщики. Описания переносятся без обрезания; данные прокручиваются вместе
с деревом. Отступы на узком экране уменьшены, маленькие иконки сохранены.

Выбор представления, область, обновление и меню находятся в одной строке.
Поиск истории и дублирующие счётчики убраны; фильтры и экспорт — в меню «⋯».
Переходы конкретного события также собраны в меню; «Назад» возвращает предыдущую
выборку того же источника и раскрытия. Смена представления сохраняет chat/run scope.

Строки раскрытия используют общий с демо компонент `rna-history-summary`:
13 px, высота от 28 px, маленькие проектные иконки, нейтральная поверхность.
Отдельные цвета, залитые строки запусков и цветные боковые полосы удалены.
Короткий результат стоит рядом с названием действия; подробности — в раскрытии
по образцу `action-detail` демо, с общими tokens границы, фона и скругления.
Селектор «Результат / Аргументы / События» и режим JSON находятся в одной строке.
Результат и аргументы — точные поддеревья загруженной проекции; усечённые,
невалидные или неоднозначные оболочки показывают причину и путь к исходным событиям.

«Состав запроса и ответа» открывает существующий инспектор с сообщениями, ответом
и JSON, а его стрелка возвращает в историю с сохранённой веткой и прокруткой.
При наличии HTTP request event id открывается именно он; источник/owner проверяется.
В представлении расхода видны отдельные значения входа, выхода и стоимости
провайдера. В списках исходных и сводных событий работают стрелки вверх/вниз и
Home/End. Браузерная проверка сравнивает оформление строки непосредственно с демо
и сохраняет снимки всех альтернативных представлений на демонстрационных данных.

В раскрытии одновременно показан один просмотрщик: данные, связи либо загруженное
содержимое. Убраны искусственный корень `data/evidence/payload`, вложенные рамки,
отдельные деревья друг под другом и постоянные кнопки у каждого узла. У JSON один
выбор вида и меню действий; отступы меньше, закрывающие скобки не занимают строки.
Копирование узла доступно по наведению и с клавиатуры, на touch значок остаётся
видимым. Исходные числа, повторяющиеся ключи, MIME, неполнота и ошибки чтения
сохранены. Счётчик и подгрузка находятся внизу. На узком экране список исходных
событий расположен над содержимым. Поля истории не включают «Применить» настроек.
Проверка: `chat-history-layout`, `run-journal`, `trajectory-json-viewer`,
`json-viewer` и workspace Inspector; Windows/WebView2 остаётся открытым evidence.

Минимальные проверки: `tests/web/chat-inspector.test.js` (реальный product DOM,
preview bridge, одна иконка, состав, раскрытия, cancel/late delivery, step routes,
узкий экран и темы), `model-context-layout.test.js` (размеры, сохранение состояния,
клавиатура, общий viewer и полноэкранная изоляция),
`model-context.test.js` (точный шаг и отсутствие fallback),
`context-usage.test.js` (граница API usage/estimate),
`workspace-inspector.test.js` (общий DOM, точные owner/session/run/step,
непересоздаваемый iframe, черновики, узкий экран и темы). Это browser/host-neutral
evidence; Windows/Office/WebView2 остаются непроверенными.

Визуальная проверка `main` от 2026-10-25: просмотрены светлая/тёмная темы,
широкая панель, узкий экран и редактор аннотаций. Найденное
[расхождение статуса шага и действия](stabilization/RISK_REGISTER.md#inspector-terminal-action-status--2026-10-25)
исправлено. Шапка workspace-запроса при 390 × 844 сокращена примерно с 260 до
205 px с сохранением вкладок и привязки к шагу. `chat-inspector`,
`workspace-inspector`, `model-context-layout` и `model-context` проходят;
проверки покрывают возврат выбора источника в Office, предварительный контекст,
Focus/Escape, узкую панель и сохранение загруженного тела при изменении размера.

Следующие ограниченные этапы:

1. Дальнейшая детализация состава: раздельная атрибуция инструкций, навыков,
   инструментов и частей смешанных сообщений; сводка в верхнем счётчике контекста.
   Порядок сообщений, покрытия, сохранённые пропуски и базовые доли уже доступны.
   Оценка следующего workspace-запроса требует отдельного compiler-контракта.
2. Причины компакции и сравнение соседних запросов по сохранённым источникам.
3. Локальный причинный граф; перенос старых экранов только после проверки
   переходов, полного журнала и экспорта. Windows qualification — отдельный gate.

### Изменение ширины панелей

Разделитель дерева в каждом разделе и разделитель правой панели перетаскиваются;
центральной декоративной ручки нет. Стрелки меняют ширину, Shift увеличивает шаг;
Home сворачивает дерево, End раскрывает до максимума; для правой панели Home/End
задают границы. Enter или двойной щелчок возвращают исходный размер.
Перетаскивание дерева за минимальную ширину сворачивает его до полосы разделов.
Кнопка навигации возвращает прежнюю ширину; состояние общее для разделов и вкладок.
Единственная кнопка сворачивания дерева стоит рядом с заголовком центральной панели,
в том числе в демо. В заголовке самого дерева второй такой иконки нет. От края
центральной панели до кнопки — 10 px, от кнопки до заголовка — 6 px; в одном
столбце крайний отступ — 8 px. Кнопка следует за границей дерева во время
анимации. Справа кнопка инспектора имеет такой же крайний отступ 10/8 px.
Мышь не оставляет клавиатурную рамку фокуса. Общая кнопка панели сбрасывает
прежний клавиатурный фокус перед нажатием мышью или касанием,
сохраняя нативный фокус мыши и видимую рамку для Tab/Enter/Space.
Escape отменяет перетаскивание;
потеря захвата, фокуса окна или скрытие вкладки завершают его и снимают подсветку.
Минимальные размеры сохраняют место содержимому. При скрытой/накладной панели
разделитель скрыт; расширение окна восстанавливает выбранные размеры.

Форк у сообщения создаёт соседнюю ветку того же документа/проекта с историей
до выбранного сообщения включительно. Исходный чат и его черновик сохраняются.
Редактирование сообщения отправляется в новой ветке. Модель выбирается в меню
над composer: вариант по умолчанию, описание, возможности и лимиты, отметка выбора.
Кольцо контекста стоит слева от названия модели. Цветного значка и пинга рядом
с моделью нет. Лампочка включает reasoning, кольцо раскрывает расход контекста.
Меню «+» содержит файл, выделение Office, материал и сжатие контекста.
Загрузка истории использует shimmer; анимации учитывают reduced motion.

Проектные чаты в рабочем UI принадлежат выбранному workspace и используют
`WorkspaceConversationService` через typed bridge. Они не наследуют Office target
документного чата. Прототип и product preview моделируют ответы в памяти.

### Панель материала

Выбранный материал и его представление — разные UI identity. Переключение
представления, версии, экспорт и удаление всегда относятся к выбранному материалу;
черновики изолированы по ID. Одна кнопка сохранения в заголовке редактора.

| Тип | Панель представления | Действия |
|---|---|---|
| Markdown | Просмотр / исходник | Сохранить исходник, отменить, версии, скачать |
| HTML | Просмотр / исходник; обновить просмотр | Те же действия; изолированный iframe |
| JSON | Данные / исходник | Синтаксическая проверка перед сохранением, версии, скачать |
| CSS / JavaScript | Просмотр текста / исходник | Редактирование, версии, скачать; код не исполняется |
| PDF | Страница, назад / вперёд | Обсудить, подключить, удалить; без редактора кода |
| Изображение | Формат | Те же общие действия; без сохранения исходника |
| Коллекция | Элемент, назад / вперёд | Общие действия коллекции |

Общие редкие действия находятся в одном меню. Повторной кнопки «Каталог» нет:
в дереве есть «Все материалы». Для бинарных демомакетов скачивание недоступно;
production viewer должен получать возможности от соответствующего владельца.
В строке материала текущего документа доступны разные действия: минус убирает
связь с чатом, корзина удаляет материал из документа после подтверждения.
Для другого документа эти действия не показываются. Markdown показывает одну
панель «Просмотр / Исходник», план — панель редактора «Просмотр / Код», без
внешних «Просмотр / Детали». PDF имеет одно действие копирования извлечённого текста.

Кандидаты на устранение дублирования:

- `chatResourcesPopover`, ручной context manager и inspector становятся связанными
  представлениями одной панели. Принадлежность ресурса и включение в запрос остаются
  разными признаками. Карточки результатов ведут в общий viewer.
- Правая панель чата показывает доступные возможности из typed Arsenal metadata;
  их редактирование ведёт в Библиотеку. Отдельного поповера «Арсенал» нет.
- Настройки агента содержат параметры выполнения; текст инструкции открывается
  в существующем редакторе Библиотеки.
- Сохранение, отмена, меню, версии и статус черновика используют общий EditorShell;
  получение данных, сохранение и guards остаются у владельца редактора.
- Кнопки undo/redo материала заменяются явной историей версий; восстановление
  сообщает о создании новой версии. Форматы экспорта собраны в одном месте.

## Общая система представления

Без framework, npm и bundler. Общий `web/css/app-product-tokens.css` владеет обеими темами,
`web/css/app-product-components.css` — деревом, меню, заголовком навигации, поиском,
иконками Office, вкладками и редактором кода; `ui.css` — компоновкой демо, `ui.js` — HTML-фабриками,
`edit-state.js` — состоянием изменений редакторов в памяти демо,
`navigation.js` и `workspace-tree.js` — данными деревьев демо,
`product-tree.js` — тонким адаптером демо к общему renderer; тематические `app-*.js`
передают ему реальные данные и действия без второго дерева. `chat-ui.js` — сообщениями и меню моделей,
`chat-timeline.js` — группировкой и раскрытием действий в переписке,
`materials-ui.js` — просмотром и действиями по типу материала, `appearance.js` —
настройками визуальных токенов, `chat-scroll.js` — позицией чтения,
`chat-demo.js` — исключительно сценарием воспроизведения, `split-layout.js` —
размерами панелей и разделителями, `screens.js` — демонстрационными экранами,
`app.js` — локальными сценариями.
Демонстрационный state/store и fixtures **не переносить** в production.

Отступ заголовка, содержимого, панели редактора и нижнего статуса задаётся общим
`--page-inset` по доступной ширине содержимого. Формы, компактные кнопки, диалоги
и разделы настроек используют правила `ui.css`; экраны не задают им inline-отступы.
Чат, composer, уведомления, текстовые/Markdown-просмотры и содержимое настроек
заполняют доступную центральную область с боковыми отступами, без ограничения
ширины колонки 720–860 px. У раскрывающихся строк хода работы область hover
включает отступ 8 px за стрелкой.
Цвета акцентов и синтаксиса принадлежат `app-product-tokens.css`, а успешные состояния используют
семантический `--success`, независимо от выбранного акцента. Адаптеры просмотров
берут те же токены. Собственные цвета документа/изображения и вычисляемые размеры
графиков, прогресса и разделителей остаются частью их содержимого или поведения.
Темы меняют общие поверхности; десять акцентов рабочего UI меняют hover, selection
и button tokens, сохраняя нейтральные фоны и границы. Встроенный Data Templates получает разрешённые
цветовые токены из оболочки сообщением `rna.appearance`; standalone версия использует
свою палитру по системной теме.

При внедрении использовать следующие границы:

| Владелец | Ответственность | Минимальный интерфейс |
|---|---|---|
| UI tokens/components | Цвет, размеры, формы, кнопки, меню, статусы | Семантические tokens и CSS-классы |
| Presentation navigation | Активный раздел, объект, inspector, возврат | `navigate({section, itemId, view})`; только UI identity |
| ScreenLayout | Полоса разделов, активное дерево, содержимое, inspector и адаптация | Общие slots и разделители; один каркас для всех разделов |
| WorkspaceTree | Документы/проекты и непосредственно вложенные чаты, поиск, row actions | Проекция списка и callbacks существующего domain owner |
| EditorShell | Заголовок, действия, состояние черновика | Title/actions/content/status от тематического владельца |
| Dialog | Доступный modal, Escape, возврат фокуса | Заголовок, содержимое, действия, исходный trigger |
| Тематический `app-*.js` | Загрузка, draft, выбор, обработка typed DTO | Явные enter/leave/render и существующий bridge |
| Shared Data Templates UI | Одни экраны в двух оболочках | Существующие browser/native adapters |

Это предложение внутренних presentation-интерфейсов. Публичные bridge DTO,
model wire и durable contracts не меняются. UI не вычисляет успешность эффекта,
не выдаёт authority и не хранит второй durable read model.

### Целевая граница демо и рабочего UI

Демо — утверждённый источник разметки, поведения и визуальных правил экранов, но
не источник runtime state. Не копировать `prototypes/ui/app.js` и его `P.state` в
продукт: эти демонстрационные действия обходят typed bridge, сохранение и
подтверждение эффекта. Не продолжать перенос как набор CSS-переопределений поверх
старых экранов. Извлекать утверждённые view и компоненты в `web/`, после чего и
демо, и продукт загружают **один и тот же** код представления. Текущий общий
navigation tree, поля навыка, вкладки редакторов и меню действий — первые такие
компоненты. Для каждого заменённого экрана удалить его прежний DOM/CSS/renderer;
переходных дублей не оставлять.

Пока общая правка автоматически отражается в обоих интерфейсах **только** для
извлечённых компонентов и общих CSS tokens. `prototypes/ui/*-ui.js` всё ещё
рисуют внутренние экраны демо, а тематические `web/js/app-*.js` — рабочие экраны.
Общие preview fixtures убирают расхождение примеров, но не превращают эти view
в общие. Новую правку внутреннего экрана следует делать в его общем view после
извлечения, с проверкой обоих consumers; изменение только демо не обновит продукт.

Тематический controller сохраняет владение загрузкой, черновиком, guards и
действиями. Он преобразует typed результат в модель конкретного экрана и передаёт
view явные callbacks. Демо подаёт в тот же view fixtures и демонстрационные
callbacks. Граница должна быть предметной (`render(model, actions)` для экрана),
а не единым универсальным протоколом для всех вкладок. Замена дизайна в будущем
потребует новых view, но не переписывания bridge и владельцев данных.

Рабочая статическая демонстрация запускает **тот же** `web/index.html`, JS и CSS,
что и WebView. Отдельный mock transport для существующего typed bridge отвечает
теми же envelopes и DTO, держит только временное состояние сценария и явно
отвергает неподдержанные команды. Описание операций для preview извлекается из
`BridgeOperationCatalog.cs` сервером просмотра; копия каталога в JS не поддерживается.
Preview проверяет реальные обработчики UI, переходы и состояния, но не
свидетельствует о выполнении Office/COM. Fixture и mock transport не входят в
production asset closure и не включаются автоматически при ошибке реального
bridge. Прямая запись fixture в продуктовый `state` удалена. Первый экранный
компонент после общего дерева — поля навыка (`app-skill-fields-view.js`): демо и
продукт создают одинаковую разметку, стили находятся в общем CSS, а сохранением
по-прежнему владеет `app-skills.js`. Остальные внутренние экраны ещё требуют
аналогичного извлечения; нынешний preview не доказывает их визуальное совпадение.

Правила композиции:

- Одно главное действие на рабочую область. Частые действия подписаны; редкие
  помещены в меню. Удаление не соседствует с сохранением без визуального разделения.
- На широком экране: узкая полоса разделов → одно дерево → содержимое;
  inspector открывается по запросу. Строки дерева — 30 px в компактном режиме, 34 px в обычном и 40 px в просторном;
  межгрупповые интервалы 3 px; сверху дерева 4 px. На сенсорных устройствах строки и hit targets увеличены.
  Иконки встроенных разделов и плагинов рисуются общим набором SVG; имя плагина
  остаётся подсказкой, а его иконка берётся из опубликованного manifest. В открытом
  широком дереве кнопка его раскрытия не сдвигает заголовок.
- До 820 px дерево по умолчанию свёрнуто. Кнопка меню раскрывает ту же левую панель
  в раскладке, без модального окна. До 620 px открытая навигация занимает место
  содержимого вместе с полосой разделов; выбор экрана/чата или кнопка возврата
  возвращают содержимое. При переходе между широким, компактным и однопанельным
  режимами временно раскрытое дерево закрывается; при возврате к широкому окну
  восстанавливается его ручное состояние и выбранная ширина. Раскрытие и сворачивание
  анимируются общими motion tokens без перерисовки чата; перетаскивание разделителя
  следует за указателем без задержки. Скрытая панель исключена из фокуса и accessibility tree.
  При ширине содержимого до 620 px inspector становится накладной
  панелью, до 420 px занимает всё содержимое. Проверяемые размеры — 360, 560,
  900 и 1600 px. Таблицы и код могут иметь собственную горизонтальную прокрутку.
- Смена раздела сохраняет черновик выбранного объекта. Отмена черновика,
  восстановление и замена содержимого требуют конкретного подтверждения.
- Loading, empty, error, unavailable, pending confirmation и unknown различимы
  текстом, не только цветом. Unknown не получает автоматического повтора.
- Доступность: native controls, подписи icon buttons, видимый focus, Escape и
  возврат фокуса, семантические заголовки/таблицы, умеренные live announcements.
- Сохранить существующие пузыри: пользовательское сообщение справа, скругление
  18 px, мягкая акцентная заливка без хвоста; ответ ассистента на прозрачной
  поверхности. Общие кнопки скруглены сильнее, кнопка отправки круглая.

## Оформление, уведомления и длинный диалог

В «Настройки → Интерфейс» доступны светлая, тёмная и системная тема, десять акцентов,
плотность, размер текста и уменьшение движения. Выбор применяется сразу и хранится
в отдельном ключе localStorage прототипа. Акцент не перекрашивает семантические
ошибки и предупреждения. Настройка движения учитывает также системный reduced motion.

Обе боковые панели используют общий нейтральный фон `--surface-subtle` в обеих темах.
Основные поверхности и границы не зависят от акцента; hover и выбор получают лишь
слабую примесь его цвета. Насыщенный акцент остаётся у основных действий и фокуса.
Внутренний отступ меню раздела компенсирован относительно заголовка панели.
Одиночные списки сохраняют нативный выбор и общую SVG-стрелку с отступом 10 px
справа; в forced-colors используется системная стрелка.

Проверка палитры и каскада — 2026-10-25, owner: Web presentation. По уточнению
пользователя сохранены существующие цвета поверхностей, hover и selection демо;
новая палитра не вводится. Прежние определения палитры в `app.css` и `app-theme.css`
удалены. Статусы, предупреждения, поля и синтаксис JSON используют существующие
семантические tokens вместо собственных светлых/тёмных цветов.
Подпись и стрелка дерева прозрачны при наведении:
единственная заливка принадлежит строке, отдельная подсветка доступна её действиям.
Вложенные кнопки не увеличивают компактную строку с 32 до 34 px. Клавиатурный фокус
использует общий непрозрачный `--focus` в обеих темах.
Выбор строк, акцента, темы и нажатой вторичной кнопки использует
`--surface-selected`; hover не подменяет выбранную заливку новым оттенком.

Оба entrypoint используют существующий каталог десяти акцентов `app-accent.js`.
Синий и фиолетовый используют оттенки демо в обеих темах; исходные пользовательские
swatches сохранены. Демо применяет каталог без записи настроек рабочего UI.
Миниатюры тем получают ту же палитру через локальные `.theme-preview-light/dark`,
а не отдельные наборы hex-цветов; выбранный акцент рассчитывается для их темы.

Остающиеся различия компоновки, не новые палитры:

| Область | Демо / рабочий UI | Оценка |
|---|---|---|
| Миниатюры тем | Высота 68 / 94 px, разные DOM и компоновка карточек | Цвета общие; геометрия ещё различается |
| Composer | Демо: радиус 13 px, максимум 780 px; продукт: 14 px и вся доступная ширина | Ширина продукта соответствует принятому правилу выше; демо требует обновления, радиус ещё различается |

Оставшиеся пункты принадлежат [Web presentation backlog](stabilization/BACKLOG.md#геометрия-компонентов-демо--2026-10-25).
Сравнение выполнено по computed styles и снимкам Chromium preview в обеих темах;
это не квалификация Windows/WebView2.

Разделитель имеет фон основного содержимого и одну граничную линию: заливка дерева
не продолжается вправо. Зона захвата остаётся 6 px; изменение ширины — общее для
всех деревьев. Декоративной ручки посередине нет.

Правила уведомлений:

- Недоступность документа относится ко всему чату: плашка под заголовком, вне скролла.
- Ошибка запроса/неподтверждённый результат требуют действия: плашка рядом с вводом,
  без потери черновика и без автоматического повторения внешнего эффекта.
- Ошибка конкретного шага находится в его группе действий. Предупреждения, влияющие
  на выводы, остаются видны рядом с итогом, даже если подробности группы свёрнуты.
- Копирование, сохранение и другие краткие подтверждения используют toast. Ошибки
  и запросы подтверждения не должны исчезать в таком уведомлении.

Подпись и знак RNAssistant перед каждым ответом не показываются; для средств
доступности у ответа остаётся название «Ответ агента». Кнопки ввода имеют промежутки
8 px, перед отправкой — 12 px; круглая кнопка отправки сохранена.

Чат строится как последовательность событий, а не фиксированная пара «ответ →
карточки инструментов». Только соседние действия объединяются в этап.
Сообщение агента, предупреждение, таблица или материал разделяют этапы; группы не перескакивают через эти границы и сообщения пользователя.
В fixtures тип сообщения задан явно (`commentary` / `answer` / `final`), а не угадан по тексту.

- Этап свёрнут в строку от 28 px: смысл, число действий, замечания; без фоновой карточки.
- Во время выполнения сообщения агента видны перед относящимися к ним действиями.
  Активная группа раскрыта, shimmer идёт по тексту активного действия. После
  явного финального ответа весь предшествующий ход этого выполнения сворачивается
  в одну строку: длительность, если известна, число действий и наличие замечаний.
  Итог, таблицы, материалы и diff остаются снаружи. Раскрытие возвращает исходную
  последовательность сообщений и вложенных действий. Остановка без финального
  ответа не скрывает ход работы.
- Внутри — строки действий; каждая отдельно раскрывает краткий результат и источник.
  Короткие детали открываются без отдельной большой карточки.
- Открытые группы и отдельные действия сохраняются при обновлениях. На сенсорном
  устройстве высота строки увеличена до 36 px. При чтении истории обновления
  сохраняют якорь прокрутки; фокус раскрытия также сохраняется.
- Ошибка до восстановления показана явно. Успешный повтор не стирает первую попытку:
  она отмечена «Повтор помог», исходная ошибка доступна в подробностях.
  При сворачивании выполнения наличие замечаний остаётся видно в его заголовке.
- Итоги, запросы подтверждения и уточнения не прячутся в истории. Материал — компактная
  ссылка, а не ещё одна большая карточка. Копирование и форк находятся под ответом.

При production-переносе группировать существующие message/activity projections,
не создавать второй event store. Статус эффекта остаётся у runtime.

Основания: существующие `groupAgentRunUpdates`, `appendAgentCompletedActions` и
`renderAgentRunArticle` в `web/js/app-agent.js`, раскрываемые действия в
`web/js/app-agent-activity.js`. Из публичных агентских интерфейсов использованы
[компактные сводки завершённых действий VS Code](https://code.visualstudio.com/docs/chat/chat-overview)
и [вложенные подробности инструментов](https://code.visualstudio.com/docs/agents/run/tools).
[Протокол Codex App Server](https://learn.chatgpt.com/docs/app-server#items)
различает сообщения, действия и фазы `commentary`, `partial_answer`, `final_answer`;
это обоснование разделения промежуточного текста и результата, а не доказательство
точного поведения desktop UI. Прямой просмотр окна Codex недоступен инструменту;
прототип не заявляет копирование его внутренней реализации.

Кнопка «К последним сообщениям» появляется, когда пользователь прокрутил вверх.
Новые события не перетягивают чтение вниз; кнопка показывает наличие обновлений.
Возврат вниз включает следование новым сообщениям. Позиция сохраняется отдельно
для каждого чата при переходах и изменении темы.

Кнопка **«Живой пример чата»** в полосе демо запускает отдельный пример из 12 этапов
(~46 секунд): три вопроса и три ответа, группы чтения и сравнения, временная ошибка,
повторное чтение, ограничения данных, частичный результат и итоговый материал.
Доступны пауза, следующий шаг и повтор. Исходные чаты не меняются; сообщение/материал
создаются только в памяти прототипа. На демо нельзя опираться как на evidence runtime.

## Единое переключение интерфейса и приёмка

Цель — один production UI в облике утверждённого прототипа. Текущий частичный
перенос остаётся рабочим baseline, но дальнейшие экраны не должны превращаться в
серию промежуточных гибридов. Визуальный reference закреплён отдельно; подключение
идёт последовательно в `main` с удалением заменённых путей. Совместимость со
старой разметкой, переключатель версий UI и параллельные экраны не нужны.

1. По таблице сопоставления ниже проверить только расхождения: какие реальные
   действия должны попасть в новый экран, какие функции демо пока не имеют owner
   и какие функции сознательно откладываются. Не оставлять работающими на вид
   demo-кнопки и не терять действующие опасные/сохраняющие действия молча.
2. Вынести утверждённую оболочку, навигацию и сами view из демо в `web` с их
   разметкой, стилями и поведением. Демо загружает эти же view; демонстрационные
   fixtures и store не переходят в продукт. Presentation получает данные и
   callbacks от существующих тематических `app-*.js` и typed bridge.
3. Подключить реальные владельцы чата, материалов, Библиотеки, VBA, проектов,
   Data Templates и настроек. У Data Templates остаётся один
   shared UI для standalone/browser и native host; экспортируемая asset closure
   обновляется вместе с ним. Runtime lifecycle, document guards, read-back и
   draft safety не меняются ради визуального переноса.
4. После подключения каждого заменённого пути удалять старые DOM/CSS/JS
   consumers. До объявления полного переноса удалить оставшиеся старые панели,
   маршруты и мёртвые зависимости; без fallback на прежний UI.
5. Запустить рабочий UI в статическом mock preview через тот же typed bridge
   transport, сначала доказав границу на одном экране с деревом, редактором и
   сохранением, затем покрыть сценариями остальные разделы. Проверять поведение
   адресными browser-тестами по риску, затем одним сквозным проходом по всем
   экранам, маршрутам и состояниям на узком и широком окне.
   Windows/Office/WebView2 qualification остаётся отдельным открытым evidence.

Внутренние проходы нужны для управляемой разработки, не для выпуска нескольких
версий интерфейса. Временный adapter допустим только при конкретной необходимости:
consumers, owner и условие удаления записываются в `MIGRATION_MAP.md`;
адаптеры совместимости со старым UI удаляются перед переключением. Размер файла
сам по себе не является причиной рефакторинга.

### Рабочий UI после переключения — 2026-10-18

Исторический срез на 2026-10-18; текущий статус Data Templates и проектных чатов — ниже.

Поправка к приёмке: подключение существующих controllers под новой оболочкой **не
завершает** перенос основных вкладок. Нужно сравнивать и внутреннюю компоновку с
прототипом при наполненных, пустых, ошибочных и выполняющихся состояниях. На
2026-10-18 внутренние экраны Библиотеки и VBA прошли адресный перенос, Материалы —
перенос каталога и просмотра; чат и оставшиеся состояния Материалов ещё требуют
сравнения с демо. Сообщение о полном переносе было преждевременным.

Принятые продуктовые решения: действия обработки, проверки шаблона, правки
словаря и просмотра результатов из демо должны получить настоящий сценарий в
native Data Templates. Проектные чаты привязаны к проекту и не получают Office
действия текущего документа. Дополнительные функции старого проекта согласуются
с пользователем **по одной до добавления** в новый экран. Для источников
подтверждена подготовка файлов с очередью и лимитами в дополнительном меню;
«Вернуть сохранённую подборку» удалено. Кнопка «Проект» теперь открывает один
выбор полного пути к `project.json` с явным открытием или созданием, а не
двухшаговую форму папки и относительного пути. Существующий application contract
остаётся владельцем binding и проверки результата.

Текущий законченный срез presentation: нативные источники имеют дерево разделов,
таблицу выбранных файлов, компактную карточку действий и один выбор проекта.
Подборка, подготовка и очередь используют прежний typed bridge. Кнопка обработки
не показывается как работающая, пока нет native dispatch и проверенного результата.
Редактор инструмента использует пять разделов демо; отдельное поле «Название»
показывает ID без новой сохраняемой модели. Флаг включения инструмента оставлен в
меню, создание копии остаётся отдельным действием. Копирование текстового
представления инструмента и обсуждение инструмента/навыка убраны. Копирование
текста навыка доступно из меню. VBA использует вкладку «История» с копиями только
выбранного модуля; обсуждение модуля и технические метаданные удалены из UI.
Заголовок встроенного навыка показывает режим чтения и кнопку создания
редактируемой копии; встроенный инструмент предлагает создать собственный.
Меню редактора VBA позволяет отменить черновик до загруженного кода и скачать
текущий код (включая несохранённый черновик) как `.bas`.
Материалы открываются таблицей из того же типизированного каталога, что и левое
дерево. Поиск и фильтры находятся над таблицей; заголовки сортируют по всем
столбцам, по умолчанию новые материалы выше. Выбор строки открывает прежний
точный просмотр/редактор. Заголовок материала и действия теперь устроены как в
демо, версии и действующие операции собраны в меню. Возврат к таблице освобождает
предпросмотр и блокируется при несохранённых изменениях. Создание самостоятельных
форматов и старые дополнительные действия редактора Материалов ожидают отдельных
продуктовых решений и проверки.
Геометрия общей оболочки теперь проверяется против демо: у всех шести разделов
левый и центральный заголовки высотой 52 px, их нижние границы соединены через
видимый разделитель шириной 1 px; ширина дерева при компактном окне — 290 px.
Палитра, линии и скругления рабочего UI используют те же tokens, что и демо,
без перекрытия прежними переменными `app.css`. Нативное дерево Data Templates
использует SVG-иконки, раскрываемые группы и поиск; поиск Библиотеки и VBA
размещён в заголовке дерева. Навигация Настроек и экран Модели используют
компоновку демо. Этот прежний срез presentation дополнен рабочими сценариями
Data Templates и проектных чатов, описанными ниже. Для прочих основных вкладок
владелец представления — тематический `web/js/app-*.js`, а не demo fixtures.

`web/index.html` использует общую с прототипом полосу разделов, палитру,
навигацию, компоненты редактора и просмотрщики. Верхние вкладки и отдельные
копии их CSS удалены. Все разделы открывают существующие реальные controllers:
чат, материалы, Библиотеку, VBA, Data Templates и настройки. Единственный DOM
Data Templates переставляется host adapter в боковую навигацию; standalone UI
сохраняет тот же исходник. Общая оболочка просмотрщиков находится в
`web/js/app-viewer-ui.js`; демонстрационные данные остаются в прототипе.
В материалах одно меню «+» содержит импорт и создание; каталог
группируется по принадлежности, а HTML-проекты — внутри своей группы. Библиотека показывает навыки, инструменты и
инструкции, CodeMirror использует общие стили. Настройки выделяют контекст и
вложения в отдельный экран, не дублируя сохранение. UserForm creation убрано из
UI; редактор кода существующих UserForms остаётся CodeOnly.
В дереве и заголовках Библиотеки показывается понятное имя навыка или инструмента;
технический ID остаётся в поле редактора и подсказке строки.

Акцент по умолчанию — зелёный как в прототипе; сохранённый выбор пользователя
сохраняется. Действия, не имеющие настоящего owner (например демо-проверка
соединения), в рабочий экран не добавляются. Проектные чаты используют отдельную
привязку к data project, описанную ниже. Реальный
выбор проекта и все операции Data Templates остаются в общем приложении; его
пустое состояние и подключение проекта отличаются от демонстрационного дерева
с готовыми файлами. Это явные расхождения, не скрытые fallback-маршруты.
В прежнем встроенном экране `#tab-workspace` оставлен один подбор источников —
из рабочей папки
через существующий project owner; браузерный File/drop-подбор удалён из этого
хоста и его scripts больше не загружаются. Самостоятельное приложение сохраняет
File/drop-подбор. Оба хоста показывают выбранный проект в общем заголовке и
открывают свои реальные настройки кнопкой «Проект»; палитра standalone совпадает
с продуктовой. Нативные вкладки теперь переключаются внутри этой же оболочки:
«Шаблоны» читают каталог проекта и открывают наблюдаемую версию как исходный JSON,
«Параметры» и «Соответствия» показывают общий словарь только для просмотра.
Черновики остаются отдельными снимками; этот прежний экран не является текущим
путём плагина Data Templates с полным набором сценариев, описанным ниже.
Рабочее дерево Office теперь строится из существующих списков документов и чатов:
компактные строки, действия, фокус и раскрытие соответствуют прототипу. Стрелки,
Home/End и поиск по началу названия перемещают фокус без выбора чата; Enter выбирает
чат, Shift+F10 открывает действия. Новый чат в приложении Office запускается из
одного меню над деревом. Выбор чата раскрывает его документ и возвращает строку в
видимую область; действия остаются у существующих chat/domain owners.
Windows/Office/WebView2 qualification остаётся открытой.

### Data Templates и проектные чаты — 2026-10-19

Иконка плагина открывает его исходный workspace в общем экране проекта. Слева
остаётся дерево проектов и чатов, в центре — общий ChatView, справа — предпросмотр.
Data Templates раскрывает внутри предпросмотра свои разделы источников, шаблонов
и черновиков, словаря, обработки и результатов.
Общая browser/native UI приложения остаётся владельцем редактирования,
проверки шаблона, очереди Worker, отмены, сохранения и экспорта. Дерево лишь
переключает его реальные представления; данные и полномочия не копируются в UI.
Заголовок внутренних разделов использует общий компонент поиска и открытия проекта. Выбор
шаблона открывает рабочий JSON-редактор; выбор группы «Шаблоны» возвращает
каталог. Навигация, сделанная во время загрузки iframe, доставляется после
готовности; mock preview отмечает готовность после начального наполнения проекта.
Завершённый подбор не занимает место над каждым экраном плагина; ошибки и
выполняющиеся операции остаются видимыми.
Обновление предпросмотра, условное «Применить», выпадающий список опубликованных
версий с действием «Восстановить» и меню действий находятся в верхней полосе
правого предпросмотра. Чаты и новый чат доступны в основном дереве проектов;
отдельное меню истории плагина удалено. Пустое состояние использует общую иконку
чата и три кнопки подсказок в стиле Office-чата.
Меню «+» проектного чата использует общий пункт «Файл с компьютера» над
«Планированием». Загруженный читаемый файл вставляет путь в черновик;
нечитаемый формат остаётся в проекте с явным сообщением об ограничении.

Проектные чаты выбираются в рабочей области через «Проекты». Application owner
показывает подключённые workspaces и чаты каждого, независимо от выбора проекта
в Data Templates. Поиск находит workspace по имени и вложенные чаты; можно
подключить существующую папку или создать новую через одну серую строку
«Новый проект» над деревом, оформленную как «Новый документ Office».
При выборе другого workspace
активный чат меняется, а история прежнего остаётся на месте. Создание,
переименование, удаление, отправка, отмена и ответы на вопросы идут через typed
bridge и общий conversation runtime. Удаление истории убирает workspace из дерева,
сохраняет его папку и файлы; повторное подключение возвращает тот же workspace ID.
В mock preview эти действия используют только память вкладки и показывают, что
модель не запускалась. Windows/Office/WebView2 сценарий ещё требует отдельной
проверки.

Вкладка «Детали» с метаданными и историей остаётся у остальных типов материалов;
для Markdown и плана она убрана вместе с дублирующей панелью просмотра.

Для прототипа достаточно JS syntax checks и браузерной проверки маршрутов,
компоновки, черновиков, подтверждений, неверного JSON, отмены и возврата фокуса.
При production-переносе выбирать существующие релевантные `tests/web` по сценарию,
добавлять coverage только при конкретном пробеле. Не запускать весь harness
из-за визуальной правки. Windows/Office/WebView2 qualification — отдельный этап;
браузерный прототип её не подтверждает.

## Сопоставление с рабочей системой — 2026-10-17

Это интеграционный прототип presentation-слоя, не второй runtime. Рендереры уже
подключены напрямую из `web/`; файлы vendor не копируются и не загружаются с CDN.
Сервер просмотра раздаёт `/` из `prototypes/ui`, `/web/` — из существующего `web/`.
Старая команда раздачи только `prototypes/ui` больше не подходит.

| Область | Решение | Подключение к рабочим владельцам |
|---|---|---|
| Деревья | Один локальный ARIA tree для прототипа и всех рабочих разделов; визуальные правила находятся в `app-product-components.css` | `app-navigation-tree.js` владеет DOM, roving focus, раскрытием и scroll position. Адаптеры передают выбранный domain item существующему controller; материалы дополнительно проверяют лимиты локального массива. Прежние renderer списка ресурсов и Wunderbaum удалены |
| Редакторы | Штатный CodeMirror 5.65.16. Отдельный Doc и undo по объекту/файлу; detach перед повторным mount | `app-editors.js`, `app-html-workspace-editor.js`, соответствующие Library/VBA controllers. Сохранение в продукте остаётся revision-aware; DOM не пишет в CAS или Office |
| JSON | `app-json-viewer.js` через `RNAssistantViewerRegistry`: дерево по умолчанию, исходник при ошибке; копирование путей и лимиты | Exact resource read/completeness передаются из текущего resource controller; не заменять parser на JSON.parse. JSON.parse в демо используется только для проверки редактируемого JSON перед сохранением |
| Текст/Markdown | `app-text-viewer.js`, Marked и DOMPurify. Текст имеет поиск, диапазоны и признак полноты | Сохранить source completeness и bounded pagination. Нельзя представлять сокращённый текст полным. Внешняя оболочка не дублирует вкладку исходника Markdown |
| Изображения/PDF | `app-resource-viewer.js` и Viewer.js: масштаб, поворот, страницы, миниатюры, извлечённый текст | PDF rasterization/extraction остаются в native resource service. Прототип создаёт только demo page images; оригинального PDF здесь нет. Blob leases освобождаются после destroy |

## Reflection and model progress — 2026-10-24

Settings → Agent exposes **Глубина рефлексии**, 0–20 (default 2). It counts accepted
reflection decisions between terminal tool results/user inputs, independently of
format and transport retries. The tooltip explains zero and the corrective request.
Office accepted reflection and tool steps keep provider reasoning through live
handoff/reopen; a tool batch shows it once, on its first activity.
Workspace/project/plugin messages have stable identities and retain unchanged DOM
nodes when new activity arrives. Their run snapshot exposes transient, bounded model
preview only for the exact running run/attempt, including a run owned by another
local process through read-only IPC; acceptance replaces it with saved messages.
Office and workspace use one run article and one live-output leaf. Token updates
change the attached text node; saved answers render Markdown after acceptance.
Accepted reflection stays expanded in the shared run history after completion.
An old-format workspace chat is explicitly read-only; unsupported
protocol bodies display a notice, never raw JSON or a silently migrated response.
Real WebView2/Office behavior remains a target-host qualification gate.

  в «Материалы» и закрытием просмотра. Общая кнопка правой панели находится в
  заголовке чата. В будущей истории ресурсов появятся «Назад» и «Вперёд»;
  недоступные действия будут видимо отключены. История относится к просмотрам ресурсов, не к
  истории сообщений или действиям агента. Строка браузера
  стоит на уровне заголовка чата; внутри страницы второго заголовка нет.

### Аннотация элемента

1. «Аннотировать» включает рамку при наведении. Клик по элементу открывает у
   него компактный редактор: отдельный номер в кружке, краткое имя элемента,
   поле комментария шириной примерно 280 px (растёт по высоте), «Готово» и
   «Отмена». Редактор размещается справа от цели, а при нехватке места — слева
   или ниже; он не выходит за границы браузера. Текст вводится в доверенном
   слое оболочки, а не в DOM просматриваемой страницы. Номера также рисуются
   поверх кадра оболочкой; только сами номера принимают клики. Они располагаются
   за краем выбранного элемента, чтобы не перекрывать соседние элементы. Выбор
   сразу создаёт одну
   локальную запись черновика в состоянии редактирования; ввод сохраняется
   владельцем общего composer. «Отмена» удаляет эту запись.
   При наведении рамка и лёгкая заливка используют выбранный акцент интерфейса;
   рядом показываются безопасные `tag#id` и размер элемента, без содержимого полей.
   После прокрутки подсвечивается элемент под курсором; выход курсора из просмотра
   убирает подсветку, если элемент ещё не выбран. Активная кнопка использует общий
   стиль нажатого toggle в браузере и «Материалах».
2. «Готово» или Enter сворачивает редактор в номер на HTML; Shift+Enter добавляет
   новую строку. Запись появляется
   **ту же запись** в списке вложений общего composer. Пустой комментарий добавляет
   выделение для диагностики с явной подписью «Только элемент». Такое вложение
   можно отправить без текста чата: принятый запрос просит описать элемент и
   уточнить задачу. Номер — локальная
   подпись в текущем черновике, не новый resource alias или ключ модели.
   Удалённые номера не переиспользуются до отправки.
3. Номер виден только при включённом режиме. Клик по нему снова открывает
   редактор. После выключения режима номера и редактор исчезают с HTML, а
   аннотации остаются в черновике и сообщениях; страница получает свои обычные
   клики, прокрутку и ввод. Escape сначала завершает редактирование,
   сохраняя черновик и сворачивая карточку, затем выключает режим выбора.
   Выключение режима при открытом редакторе тоже сворачивает его без потери текста.
4. Над composer виден компактный пункт «Аннотации · N» для ещё не отправленных
   вложений. Наведение раскрывает
   список, клик закрепляет его для клавиатуры и сенсорного ввода. Строка списка:
   номер, короткий фрагмент цели, текст комментария, «Показать», «Изменить»,
   «Удалить». «Показать» открывает точный ресурс справа и подсвечивает цель;
   «Изменить» открывает тот же редактор. Удаление убирает запись из черновика,
   списка и номер с HTML одним действием. При нескольких аннотациях одного
   элемента номера собираются рядом, без перекрытия элемента целиком. Номера
   являются кнопками с доступным именем; список и редактор работают с клавиатуры.
5. Черновик и номера привязаны к точному чату, ресурсу и revision. При reload
   того же источника расположение перепроверяется; исчезнувшая или неоднозначная
   цель остаётся в списке с явным статусом, без привязки к похожему элементу.
   На отправке каждая запись принимается один раз через существующий input/CAS.
   Отправленные аннотации видны в сообщении как ссылки на источник; на странице
   их номера при доступном исходном revision открывают просмотр. История сообщения
   immutable, поэтому последующее исправление комментария — новое сообщение.

Текущий HTML Inspector в «Материалах» и правом браузере открывает один редактор
комментария у элемента.
«Готово» готовит один снимок с комментарием в CAS и добавляет его в общий Office
черновик; при включённом режиме номер остаётся поверх страницы и следует за
прокруткой. Клик по номеру
или «Изменить» в списке над composer открывает редактор, сохранение заменяет
подготовленный снимок, «Показать» прокручивает к точной цели, «Удалить» убирает
вложение и номер. Исчезнувшая или неоднозначная цель помечается в списке.
Выключенный режим
оставляет страницу интерактивной. Номера выделяются из того же защищённого
черновика и не переиспользуются до отправки. Незавершённый комментарий и
его привязка к элементу сохраняются в защищённом черновике общего composer;
при повторном открытии редактор продолжает тот же текст. Пока аннотация не
завершена или не удалена, отправка сообщения недоступна. Подготовленные
аннотации восстанавливаются из CAS при открытии черновика.
Отправленные аннотации показываются в истории сообщения и, при включённом режиме,
номерами на совпадающем revision HTML. Номер открывает комментарий для чтения;
правка immutable сообщения
не допускается. Одновременно отслеживаются последние 100 загруженных аннотаций;
ссылка в более старом сообщении выводит его номер для просмотра. Общая инструкция
агента требует найти однозначный реальный исходник и применить существующий patch;
автоматическое доказательство DOM→source и визуальная проверка правки ещё открыты.
Для плагина host связывает точный frame/instance,
staging и submit проверяют release и workspace. Второй формат аннотаций не вводится;
реальная Windows/WebView2 проверка остаётся открытой.


## Визуальные ответы в ленте — 2026-10-25

Owner: Web chat presentation (`app-chat-visuals.js`), общий Markdown enhancer.
Office, project и plugin используют существующие message/agent renderers.
Закрытые fenced-блоки `mermaid` в завершённых сообщениях превращаются в схемы
при появлении в области просмотра; `html` запускается вручную кнопкой ▶.
Это один переключатель: при подготовке и просмотре он становится ■, после
остановки или ошибки подготовки снова ▶. Остановка отменяет и ожидающую загрузку.
Стриминг и незакрытые fences остаются кодом. Исходник можно раскрыть и скопировать;
увеличение сохраняет iframe, остановка его удаляет. Переключение чата освобождает
preview; возвращение не запускает HTML автоматически. Асинхронные загрузки
отброшенного сообщения не вставляют результат в новую ленту.

Mermaid 12.2.0 поставляется локально: strict, без конфигурации из сообщения,
30 000 символов / 300 edges. SVG проходит sanitization и показывается в inert
sandbox iframe. HTML ограничен 200 000 символами, использует `allow-scripts`
без same-origin; CSP запрещает сеть, внешние зависимости, вложенные frames,
формы и workers. Локальный ECharts внедряется при обращении к `echarts`.
Resource/fetch/Office bridge в preview не предоставляется; сообщения об ошибках
принимаются только от текущего iframe. WebView2 фиксирует принадлежность frame
к chat-preview до исполнения его скриптов и запрещает внешнюю навигацию,
включая отдельное исключение навигации для plugin entry pages.

Таблицы имеют тонкие разделители строк, отступы, горизонтальную прокрутку и копирование.
Поддерживаются обе темы и узкая лента. Mermaid перестраивается при смене темы;
работающий HTML сохраняет состояние и тему запуска до следующего запуска.
Это presentation существующего message, не новый artifact/store/wire contract.
Навык `common.chat_visualization` описан в [Skills](skills.md#chat-visualization).

Проверки: `tests/web/chat-visuals.test.js`, raw HTML/JSON, stream render cost,
shared workspace chat layout и vendor gate. Реальная проверка навигации и
изоляции в Windows/WebView2 остаётся открытой. Sandbox ограничивает authority,
но не гарантирует CPU isolation: бесконечный JavaScript может затормозить renderer.


Кнопки блоков Markdown/визуализаций используют общий `icon-btn` демо:
SVG без видимого текста, 28 px (40 px touch), `title` и `aria-label`,
`aria-expanded` для раскрытия. Рабочий пример доступен через preview-server:
`/preview/web/?scenario=visuals`; сообщения приходят из mock bridge в настоящий
ChatView, данные явно демонстрационные. HTML запускается вручную.

Визуальная подача: одна внешняя рамка, радиус 18 px и `surface-subtle` у схем
и таблиц. Нет видимой подписи Mermaid/HTML и внутренней полосы заголовка;
кнопки расположены сверху, как у кода и таблиц. SVG имеет прозрачный фон; обычные flowchart-узлы
скруглены, смысловые формы условий сохраняются. Навык рекомендует HTML/CSS
для сложных карточных схем с подзаголовками и иконками; запуск остаётся ручным.

## Подписи источников в результатах tools — 2026-10-26

Owner: ToolResultPresentationService и общий Web renderer; [матрица результатов](audits/tool-result-presentation-matrix.md).
В раскрытом шаге document/workspace-чата `E7 · действие · объект` обозначает сохранённую операцию.
Подпись `R3@v1 — src/A.cs, строка 42: «искомый текст»` раскрывает тело того же
canonical read. Текст/CAS и evidence не подменяются похожим activity preview.
Одна строка/диапазон, страницы, символы, таблица или tree pointer отображаются
по своему typed selector. Цитата ограничена; полное доступное тело — внутри карточки.
Поисковые совпадения показывают target/координаты/snippet без R, пока нет точной
per-item связи. HTML в подписях остаётся текстом. В диагностике общий formatter
работает в «Источники и полнота» с actual request и подтверждённой доставкой тела.
Клики раскрывают сохранённое; переход к live-редактору и citations в произвольном
тексте ответа не реализованы этим срезом. Media использует существующие viewers.
Project/plugin читают тот же typed preview из своей сессии по точным workspaceId,
sessionId, RunId и ToolCallId; ответ с чужой областью не отображается. Сравнение
из Office journal для workspace не подставляется. Свёрнутая строка показывает действие,
конкретный target и исход попытки; до завершения target уже виден. Например,
«Изучаю · excel-analysis», затем «Чтение навыка · excel-analysis · Загружено».
Raw JSON и content blocks берутся из одного retained result/CAS; activity raw не дублируется.
Actual/intended diff имеют раздельные счётчики; отсутствующие сравнения не заменяются нулём.
Domain-specific counts/diffs и Windows delivery остаются отдельными gaps.

PDF показывает `Отчёт.pdf, страница 2, символы [4, 32)` вместо `pdf-page:1`.
Полнота выбранного фрагмента, всего источника и сокращение UI различаются; карточка
поясняет извлечение текста и границы OCR/визуального просмотра. Media имеет подпись
объекта и сохранённый статус подготовки без выдуманной R-ссылки на бинарное тело.
Раскрытие не делает live read; фактическая отправка остаётся в диагностике запроса.
Таблица, список и текст составного ответа показываются одновременно. Отсутствующее
сравнение мутации сопровождается пояснением подтверждённого изменения, отсутствия
изменений либо неизвестного эффекта, без фиктивного `+0/−0`.
